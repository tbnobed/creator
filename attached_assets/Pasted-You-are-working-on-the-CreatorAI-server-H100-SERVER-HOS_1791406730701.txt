## Steps

1. Before changing anything, record the current state:
   - `nvidia-smi` output
   - every CreatorAI container, service and ComfyUI instance, and which GPU each one uses
   - the relevant config files: docker-compose, env files, ComfyUI launch args, and the GPU Servers settings in the portal
   Save all of it to `~/mig-migration/before/` so you can roll back.

2. Drain the CreatorAI render queue. Let in-progress jobs finish, pause new job intake, then stop every process using either H100. Confirm with `nvidia-smi` that no processes remain.

3. Install mig-parted:
   go install github.com/NVIDIA/mig-parted/cmd/nvidia-mig-parted@latest
   sudo cp ~/go/bin/nvidia-mig-parted /usr/local/bin/

4. Create /etc/nvidia-mig-parted/config.yaml:
   version: v1
   mig-configs:
     obtv-split:
       - devices: all
         mig-enabled: true
         mig-devices:
           "4g.40gb": 1
           "3g.40gb": 1

5. Apply the layout:
   sudo nvidia-mig-parted apply -f /etc/nvidia-mig-parted/config.yaml -c obtv-split
   If it reports a pending GPU reset that won't clear, reboot once and apply again. Run `nvidia-smi -L` and confirm each GPU shows a 4g.40gb slice and a 3g.40gb slice. Record which MIG index maps to which profile. The 4g slice is expected at index 0, but verify it, and adjust the assignments below if the order differs.

6. Make the layout persist across reboots. Create /etc/systemd/system/mig-layout.service:
   [Unit]
   Description=Apply OBTV MIG layout
   After=nvidia-persistenced.service
   Before=docker.service
   [Service]
   Type=oneshot
   ExecStart=/usr/local/bin/nvidia-mig-parted apply -f /etc/nvidia-mig-parted/config.yaml -c obtv-split
   RemainAfterExit=yes
   [Install]
   WantedBy=multi-user.target
   Then run: sudo systemctl daemon-reload && sudo systemctl enable mig-layout.service

7. Update CreatorAI to use the slices:
   - Pin each container or ComfyUI instance with `NVIDIA_VISIBLE_DEVICES=<GPU>:<MIG>` (for example `0:0`), using the runtime: nvidia setting. Use the index form, not MIG UUIDs, because UUIDs can change when slices are recreated at boot.
   - Inside each container the slice appears as cuda:0. Remove any hardcoded `--cuda-device 1` or `CUDA_VISIBLE_DEVICES=1` that assumed whole GPUs.
   - Each slice has about 40GB of VRAM instead of 80GB. Check any ComfyUI flags that assumed the full card (such as --highvram or model-preloading settings) and adjust them so models load within 40GB. These models already run on 32GB RTX 5090s elsewhere, so they fit.
   - Update the portal's GPU Servers section and queue routing so video jobs go to 0:0 and 1:0, and image and H3 jobs go to 0:1.
   - Do not route any job, container or process to slice 1:1.

8. Verify. Run one real test job of each type and confirm it completes with correct output:
   - a Wan2.2 video on 0:0
   - a SkyReels video on 0:0
   - an LTX video on 1:0
   - a FLUX image and a Kontext edit on 0:1
   - an H3 job on 0:1
   - a Long-Form multi-shot job end to end
   - the voice clone / Chatterbox TTS service, if it runs on this server
   For each one, record render time, peak VRAM (from `nvidia-smi` during the job) and any errors. Confirm `nvidia-smi` shows nothing running on slice 1:1.

9. Test a reboot. Reboot the server, then confirm that the MIG layout comes back automatically, all CreatorAI services start on the correct slices, and one image job and one video job succeed.

10. Resume the render queue.

## Rollback

If any model cannot run within its slice, or a critical CreatorAI feature breaks and you can't fix it, roll back:
- sudo systemctl disable mig-layout.service
- sudo nvidia-smi mig -dci && sudo nvidia-smi mig -dgi
- sudo nvidia-smi -mig 0 (reboot if required)
- restore the configs from ~/mig-migration/before/ and restart CreatorAI
Then report what failed.
